# IELTS Learning Platform · Milestone 0 architecture v1.3

**Status** Remediated proposal for Product Owner review. Milestone 0 remains open. Milestone 1 requires separate explicit authorization.

## 1. Authority and architecture

[Authority index](DOCUMENT-AUTHORITY.md) governs precedence. The [decision register](DECISION-REGISTER.md) preserves D01–D11 verbatim from v1.0. Technical contracts below are proposed, with choices and gates in the decision and [ADR registers](ADR-REGISTER.md). [Traceability](MILESTONE-0-TRACEABILITY.md) defines acceptance cases. The original PRD retains authority over product requirements outside explicit supersessions.

Proposed deployment is one HTTPS ingress routing UI to Next.js/TypeScript and /api/v1 to a private Spring Boot modular monolith backed by PostgreSQL. Backend modules are identity, content/Reading, question, assessment, vocabulary and progress. Flyway, JPA, OpenAPI and exact runtimes await approval. For M1, browser-fetch private data and avoid personalized SSR. Use host-only Secure, HttpOnly, SameSite=Lax cookie scoped to /api/v1. Cookie emission and logout follow §3.4. Preserve the Spring Boot and PostgreSQL directions already recorded. Keep other provider integrations and later-release features deferred. Email verification is governed separately by §2 and TECH-03.

## 2. Registration and verification

### 2.1 Identity and tokens

Users have UUID PK, unique nonnull canonical email, display name, PENDING/ACTIVE/DISABLED status, password hash, verified timestamp/method, monotonic security and email revisions, and UTC timestamps. Normalize email consistently without provider alias folding. PENDING has neither hash nor verification timestamp. ACTIVE requires both. A disabled formerly pending identity may have neither. Enforce matching nullness, and require verification method whenever verified. Roles have UUID PK and unique LEARNER/TEACHER/ADMIN codes. user_roles has PK (user_id, role_id), required FKs to users and roles and nullable assigned_by FK to users. Public registration inserts PENDING plus LEARNER atomically, without a password.

Verification tokens have UUID PK, required user FK, email revision, unique digest, issued/expires timestamps and nullable consumed/invalidated timestamps. Generate 256 random bits and persist only the digest. A partial unique index on user_id where neither consumed nor invalidated permits one outstanding row, even after expiry. Under the user-row fence, invalidate an outstanding row before inserting a replacement. Issue, resend, consume, disable and address change serialize against the same user row. For token consumption, use digest lookup to identify the candidate user, lock user then token, and recheck digest, state, email revision, expiry and one-use state. Activation atomically sets the new adaptive password hash and verified timestamp, transitions to ACTIVE, consumes token and invalidates siblings. Rollback restores all state. Initial or duplicate registration and resend cannot modify an existing profile or password. Activation issues no authenticated session.

### 2.2 Delivery, timing and browser boundary

A valid request from an eligible source returns a generic 202 independent of account status, issuance throttle or delivery outcome. Count source limits before account lookup, and account buckets by canonical address in equivalent fashion for existing and nonexistent addresses. Source throttling is uniform. Use a common minimum response window after parsing/rate checks (proposed 300 ms), with bounded admission and database work and no synchronous SMTP dependency. Measure observable timing distributions under load before enabling production. Do not claim exact indistinguishability. Report delivery outcome through bounded internal metrics only.

Before token issuance reserve bounded volatile mail-queue capacity or leave the request on the generic no-issue path. Commit token state before handing raw token to the reserved in-process queue. Release capacity on rollback. Queue loss on crash does not activate the user; a later resend supersedes outstanding tokens. Retry a transient send failure at most once after rechecking live generation and expiry. Delivery may still race resend after the eligibility check. Only the current token can activate. Apply TECH-04 cooldown, resend and source limits. Unauthenticated resend can supersede a valid earlier link; use throttling and clear expired/superseded recovery UX. Provision real delivery only when approved. Unconfigured production register/resend return uniform 503 before mutation; dev/test adapter never runs in production.

Use configured HTTPS origin and put the token in the fragment. GET /auth/verify-email is an inert confirmation page with no auth creation, consumption or activation. Use no-store, no-referrer, restrictive CSP (only the designated first-party bootstrap, no third-party scripts, framing, analytics or worker registration) and no URL/token logging. The first script reads then removes fragment via history replacement before other work, keeps it only in memory, and clears it when leaving or restoring the document from a browser history cache. Disable link tracking/rewrites for verification mail. No token echo, storage, telemetry or cached hydration. User explicitly submits token and new password with session-backed CSRF. On stale CSRF obtain a fresh pre-auth token and allow a deliberate retry while the verification token remains in memory. Reload or lost fragment leads to reopen-email/resend UI. The link may be visible to the recipient or their browser tooling before removal; publish the limits of the guarantee.

### 2.3 Registration admission and timing contract

Proposed TECH-04 envelope for register and resend: require a valid PREAUTH token, a JSON body ≤8 KiB and valid field shapes. Start the acknowledgment clock after validation, before account lookup. Check source bucket first; apply equivalent canonical-address buckets without inspecting status. Cap admitted operations at 16 concurrent requests and 20/second service-wide, with no waiting for admission slots. A source/global rate or concurrency limit returns 429 ADMISSION_LIMIT with Retry-After: 1 or the source bucket reset, independent of account. Account bucket, absent/duplicate/ineligible user, unavailable volatile mail slot, locked row, and definitively rolled-back database timeout all produce the same empty-detail 202 acknowledgment, including status, body and headers. Store neither an account state marker nor a delivery marker in the response.

Within that path use a 20 ms DB lock bound, a 50 ms statement bound and a 150 ms whole operation deadline including pool acquisition; cancel and roll back on budget exhaustion, never allow an unobserved transaction to continue. Return generic 202 on uncertain outcome with no mail emission unless commit is known; reset the connection before pool reuse and let resend recover any committed pending token. Release a reserved mail slot exactly once on no-issue, rollback, ambiguity or handoff failure. Approved production configuration failure is uniformly 503 before lookup. Delay the generic acknowledgment until 300 ms elapsed. Delay applies outside the transaction, pool and mutation slot; ingress limits cap total pending responses. Explicitly returned 429/503 have their own account-independent paths. Mail IO happens after known commit and never on the response path.

Proposed production timing acceptance baseline: isolated same-region ingress/load generator, 10 valid requests/second, 10-minute warm-up, at least 500 samples per cohort and route with fixtures/preregistered order. Compare status/header/body, and absolute between-cohort p50 and p95 differences ≤15 ms and ≤30 ms respectively among generic-202 cases. At least 99% of those responses within 300–450 ms at ingress. Include locked row, full mail queue, existing pending/active/disabled and absent addresses while keeping source/admission buckets comparable. Use unique test identities/controlled clock for account throttles. This is a measurable tolerance for the stated load, not a guarantee at arbitrary load. Test admitted overload independently. If targets fail the public production routes stay disabled until the owner accepts corrected evidence. Foundation tests use controlled clocks and dev delivery, without depending on real SMTP.

## 3. Session and concurrency

### 3.1 Sole authentication gate and Spring integration

Propose one serving application process, process-local account bindings, and PostgreSQL account revisions/fences shared with operator processes. No sticky multi-instance deployment or automatic takeover of an unconfirmed old process. At cutover, stop new ingress to the old process, drain or terminate and confirm it has exited before admitting traffic to the replacement. Fail closed with the route unavailable if exit cannot be confirmed. Crash loses all app sessions; restart always requires login. Test this operating constraint on the selected deployment before enabling authentication.

The authoritative binding is keyed by account and records a server boot identifier, unique generation, digest of opaque session ID, account security revision, authentication time, last qualifying activity and absolute expiry. Only a request whose binding and authoritative ACTIVE database row match may establish authentication. A stored Spring Security context is transport/cache material. Use a version-pinned JSON login integration with explicit SecurityContextRepository persistence and a gate after context load and before authorization. For each protected REQUEST, ERROR, FORWARD and ASYNC dispatch, revalidate or deny. Do not resume a protected asynchronous task from inherited context alone. Recreate authorities from state pinned to the matching revision. Clear rejected context; no fallback bearer, cache-only or container-only authentication.

Use server time with a nondecreasing elapsed-time source for process-local expiry. Reject at idle >= 60 minutes or absolute >= 7 days. Qualifying successful protected application work advances last activity monotonically, capped by the lifetime cutoff. Public reads, failed calls, health, static assets, polling and CSRF bootstrap do not touch the authoritative idle clock. Configure backing authenticated session retention to cover the entire 7-day absolute window and prevent container TTL/touch from granting extra time or ending an otherwise valid binding early. Cleanup retires all expired/revoked storage under exact generation checks. Bound anonymous CSRF sessions separately (proposed 15-minute lifetime, source admission limits and bounded cleanup). No raw cookies or synchronizer tokens enter logs.

### 3.2 Login, revocation and failure ordering

Verify the password outside the fence, then take the DB account row lock and process-local account guard in §5.3 order. Recheck the credential snapshot described in §3.4 under the account-row fence. Create a fresh server session ID and fresh CSRF state without emitting a cookie yet. Persist the new Spring context as provisional. Stage the new generation under both locks after context preparation and durable recheck. Hold the local guard through DB completion and expose the binding and cookie only after successful commit. On definitive rollback discard provisional state and restore the unchanged prior binding before unlocking. On uncertain commit invalidate the affected bindings and require re-login. If a durable mutation commits between login commit and cookie delivery, request-time revision checks reject the stale cookie. If publication succeeds but response issuance reports failure, compare-and-revoke only that generation; never resurrect the prior one. A lost response after it was handed to the network is indistinguishable from delivery: only the current binding is valid, and the user may log in again to replace it. No provisional context can authorize. No unbounded local lock registry; use bounded striped guards in deterministic order when more than one is needed.

Credential changes, role changes, disablement and recovery take the same DB fence and advance security revision in the transaction. Protected writes take account row and local guard, revalidate generation/revision and expiry before mutation, and hold through commit. The write is ordered before revocation or rejected. A write authorized before expiry may commit under its bounded transaction budget; new admissions at the boundary fail. For supported protected reads materialize the permitted projection under the fence before release. External operator mutations use the database fence even when no local guard is available. A revision mismatch denies the next request immediately after the durable change regardless of local eviction. Logout and cleanup compare exact binding, never delete a replacement, and never depend on browser state for revocation. A DB outage fails private authentication closed. Transaction cancellation/crash has no speculative success response.

### 3.3 Cookie and CSRF ordering

Same-origin HTTPS, private API, host-only Secure HttpOnly SameSite=Lax cookie scoped to /api/v1. Use separate pre-auth cookie and authenticated cookie names so late token bootstrap cannot overwrite authentication. GET /api/v1/auth/csrf uses the explicitly requested scope in §3.4; response has token and header name, no-store. All browser writes require X-CSRF-TOKEN in the expected session, including public registration, verification, resend and login. Successful login rotates session and CSRF; client bootstraps AUTH after login and PREAUTH after logout. Verify that login clears old CSRF before publishing the authenticated replacement. Public Reading never creates a session. Stale CSRF returns generic 403; refresh without silently retrying a non-idempotent command.

Coordinate login/logout across tabs using a same-origin browser coordination lock where supported. Logout revokes the exact server binding and returns 204; under this proposal it sends no asynchronous authenticated-cookie clear that could erase a later login. The revoked cookie is inert until replacement or its bounded expiry. Logout clears the app's private UI/token state. Browsers can still reorder two login responses. If a stale cookie wins delivery, protected access returns 401 and the UI clears private state and offers one bounded reconciliation followed by explicit re-login. It never retries stale authenticated writes or promises latest-login cookie preservation. The server retains at most one valid binding throughout.

### 3.4 Credential snapshot and Spring integration contract

Read (user_id UUID, password_hash nullable text, status enum, security_revision nonnegative bigint) as one result from the primary in a single statement. Verify exactly that hash outside the fence, or do equivalent dummy hash work for a missing/ineligible account. Then take the same user-row lock and local stripe and compare captured user ID, ACTIVE status, revision and hash to the locked row. Never relabel a verified hash with a newer revision. Any credential, verification eligibility, status or role mutation increments the single durable security_revision in its own transaction. Pure profile changes do not. Reject overflow and stale expected revision; no separate password version. Rejected login produces generic 401 and leaves the old binding untouched. See §3.2 for rollback or uncertain completion after provisional context preparation.

Proposed integration boundary for the approved Spring Security version in TECH-01: use a dedicated server-side session/context repository behind Spring's SecurityContextRepository, and a session-backed CSRF repository with explicit scope. The frontend never supplies identity, context or revision. Suppress servlet HttpSession/request-cache creation, form login, automatic logout cookie changes, default CSRF cookie handling and fallback authentication for these routes. No JSESSIONID or implicit Set-Cookie. The explicit cookie writer is the only emitter. PREAUTH and AUTH use distinct opaque cookie names with the same secure scope, separate namespaces and no context in PREAUTH. Repeated cookies of the same configured name are invalid for that namespace. Server caches may recover candidate context by AUTH cookie, but never grant access without the generation, digest, boot and primary revision check.

Sequence: ingress route/size checks → exact route scope selection → load candidate context → mandatory binding gate for protected routes → CSRF check on unsafe routes in the chosen scope → service capability/ownership and mutation fence → commit → response/cookie. Failed or unrecognized dispatches deny by default. Protected REQUEST, FORWARD, ERROR and ASYNC re-evaluate the protected route and binding or give a safe response without private data; no inherited authentication across async execution. Clear thread-bound context on dispatch exit, and do not persist candidate authentication from generic error/redirect completion. JSON login explicitly stages context and updates the authoritative binding only through §3.2, issuing AUTH after known commit. No competing persistence/filter path promotes a provisional context.

| Route class | Namespace and expiry handling |
| --- | --- |
| GET /auth/csrf?scope=PREAUTH | Only PREAUTH; issue/reuse a bounded anonymous session. Ignore AUTH whether absent, live or stale. |
| POST /auth/login, /auth/register, /auth/verify-email, /auth/resend-verification | Only PREAUTH synchronizer token; ignore AUTH for validation, allow explicit new login to replace the target's binding. Consume/invalidate the used PREAUTH session on successful login. No success path grants auth except login. |
| GET /auth/csrf?scope=AUTH and private reads | Require current AUTH; missing/stale/revoked is 401 without PREAUTH allocation or promotion. |
| Private writes including logout | Require current AUTH before CSRF; invalid binding 401, then absent/mismatched AUTH CSRF 403. |
| Public Reading, verification-page GET, health | No context or session required, no cookie allocation. |

Client serializes same-scope CSRF bootstrap locally and across tabs where available. Keep token in memory per scope. A late same-scope response can still mismatch the cookie selected by the browser; on 403 discard that scope token, obtain one fresh token, and require a deliberate resubmit for writes. On 401 discard private state; never retry an authenticated command with PREAUTH. Fresh tokens use independent namespaces. This accepts bounded sign-in recovery when concurrent AUTH responses arrive out of order and preserves §3.3's no-clear logout.

## 4. Admin lifecycle

Provision only through an explicit authenticated deployment operator command reading managed deployment configuration. No startup hook or public API. Identity foundation seeds a singleton governance row before any bootstrap. Under its DB row lock, test durable bootstrap completion marker, existing Admin and canonical-email collision. Create the dedicated ACTIVE account, ADMIN grant, marker and success audit in one transaction. Existing ACTIVE or PENDING identity collisions fail without mutation. A completed marker makes replays no-ops. Record denied outcomes separately, with a correlation ID and no secrets. Retire bootstrap configuration after success. Role definitions and the governance lock row are identity foundation data; no credential is seeded.

A usable Admin is ACTIVE with a valid credential, verified evidence and ADMIN membership. For a dedicated operator identity, require independently verified control of the configured mailbox, recorded as operator-attested evidence with actor IDs and timestamp. Public users follow normal mailbox-token verification. Compute the post-change usable Admin count under the governance lock for every Admin eligibility mutation, including cleanup, deletion, role changes, verification changes and credential invalidation. Ordinary changes must leave one usable Admin once initialized. Runtime DB role cannot directly write roles, state or credential columns; reviewed identity routines are the only write boundary, with admin eligibility operations always taking governance first. M1 has no public role or recovery management routes.

Recovery requires separate authenticated operator and approver identities with distinct deployment capabilities. Store a scoped, expiring one-use approval tied to target and allowed action; consume under governance lock in the recovery transaction. Reject self-approval, missing/expired approvals, wrong targets, public account promotion or restart-triggered bootstrap. Reset a dedicated account, or create its verified replacement before revoking the old usable Admin inside the same transaction. Advance affected security revisions and use §3.2 fencing; deliver replacement credentials only through an approved managed channel. Audit success with the transition and one-use approval, and failed attempts separately. Audit append interfaces prohibit app update/delete; operational retention and access follow TECH-12. Recovery never resets bootstrap completion.

An operator-supplied string is not authority. The designated approver validates control of the exact canonical mailbox, using a deployment-approved confirmation challenge or independent evidence bound to the canonical address, and records an opaque evidence reference. The execution request binds approval ID, action, target, revision and exact replacement email. If reset, the mailbox is still the existing approved dedicated verified identity. If replace, proof is for the named replacement. TECH-05 must approve the evidence flow, actor mapping and secret handoff before use; this proposal creates no public verification exception.

Approval creation and consumption take governance, relevant user rows by ID, then approval row when present (§5.3). Lock and re-read all fields and target revision after locking. A verified operator can execute only the exact unexpired, unconsumed approved payload within their mapped scope, and only for a still-eligible dedicated Admin. On replacement, canonical uniqueness failure rolls back approval, credential work and success audit together. On success consume once, update/replace identity, increment affected revisions and check at least one usable Admin under governance before commit. Insert linked success audit in that transaction. Separately append sanitized denial using an authorized append-only boundary after rollback. Protect approval and audit retention under §5.5.

## 5. Logical ERD and publication

All entity IDs are UUID PK unless specified. Use UTC instants and required FKs unless explicitly optional. Users own attempts, vocabulary and progress. Authors reference users; topics optionally categorize passage versions. Stable passages and exercises each point to their own current edition. Each exercise belongs to one stable passage and every exercise edition pins an exact passage edition. Passage editions contain paragraphs and optional language translations. Exercise editions contain groups, questions, ordered options, protected marking, explanation, evidence and public sample membership. An attempt pins one exercise edition and initializes one item per question.

### 5.3 Global locks, publication and snapshots

All writers use this order and acquire their entire footprint before mutation: (1) singleton Admin governance row when Admin eligibility is affected, (2) DB account rows sorted by UUID, (3) process-local account guard stripes sorted by stripe index, (4) token/approval rows sorted by ID when applicable, (5) stable passage rows sorted by ID, (6) stable exercise rows sorted by ID, (7) Exam deadline capacity buckets sorted by UTC bucket start, (8) attempt rows sorted by ID, (9) owned child mutations. Skip unused levels, never acquire an earlier level while holding a later one. No child-specific prelocking or lazy ORM writes before parent fences. Cross-process identity writers take the DB prefix. System expiry workers take an attempt lock only and never acquire account/content locks. Protected attempt writers acquire the identity prefix, then attempt; fresh starts acquire the identity and content prefixes, then initialize the new attempt/items. An owner-scoped replay can be looked up without first taking an attempt lock or acquiring content locks. Foreign-key checks target existing, non-deletable parents for published references. Draft deletion holds its stable parent locks. Operational operations touching multiple resources must predeclare and sort them; if the set changes, discard and retry the transaction. Enforce bounded lock/statement/transaction budgets. Abort on deadlock/serialization error, and retry a bounded number from outside the transaction only for safe replayable operations. Never emit success before commit.

Application, worker and authoring DB roles have no direct content-table DML. Narrow database write routines validate required draft state, current pointer targets and revision under the stable parent locks. Give the migration/maintenance identity separate, restricted ownership without runtime credentials. The database write boundary enforces: freeze is one-way; insert into a frozen version, move into/out of one, update/delete a frozen row or descendant all fail; updates of published pointers only accept validated frozen versions belonging to the stable parent or null. Make guards apply to every graph table, including options, translations, marking, evidence and samples. Protect stable identity ownership/parent assignment from mutation that changes historic eligibility/pinned membership. Verify at the service boundary author/publisher principal and role using the revision fence before invoking the restricted writer. No general-purpose draft/admin bypass for past editions.

In one transaction, lock passage(s) then exercise(s), validate scope, current draft revision, complete graph and §7.3 limits; freeze children and version, then switch eligible pointers. Start holds the same relevant locks, rechecks eligibility and pins that committed version. Parent republish may hide stale exercise editions until coordinated republish. Withdrawal clears eligible pointer(s), leaving the frozen graph intact. Published content is retained and physically undeletable through supported runtime paths. Ordinary withdrawal leaves prior owners' pinned recovery, submission and review under the proposed policy. Exceptional takedown requires separately approved policy. Failure at any freeze or pointer step rolls back the whole change.

Public eligibility is current frozen PUBLIC passage; an exercise additionally needs a current frozen PUBLIC exercise edition pinned to that exact passage edition. Each public response, including eligibility, count, paging, membership and projection, uses one database snapshot (single statement or read-only repeatable-read transaction). Materialize DTOs before releasing it; no lazy fetch from a newer snapshot. A request whose snapshot precedes withdrawal may return the coherent previous edition. A fresh snapshot after commit cannot. SSR must use that same materialized projection; no mixing fragments from independent editions.

### 5.4 Privileged database write boundary

Logical contract only. Choose concrete routine names and toolchain after approval. DB roles are independent of application roles. An authenticated application service is the trusted end-user binding boundary: its dedicated DB role can invoke only listed routines and supplies a UUID/revision taken from the authoritative gated request, never a body or arbitrary request header. The database rechecks the supplied revision, active role and resource scope in the same transaction. The database does not independently attest a browser principal, and compromise of a trusted writer is outside that software authorization guarantee. Deployment operator/approver authority instead comes from their distinct trusted database login mappings, not supplied actor IDs or session flags. Measure runtime grants against this matrix.

### 5.6 Fresh start transaction and canonical identity

Use READ COMMITTED for fresh starts. Under the account/revision and local guard prefix, check a prior key for the authorized owner. Match request pair against immutable stored mode and stable exercise ID derived through the pinned edition; never copy a second exercise ID from the request. Existing matching key bypasses only fresh content eligibility, not current verified LEARNER/ownership. A different pair conflicts. On a new key acquire stable passage then exercise locks in §5.3 order, recheck parent membership, then issue a **new statement after both locks** to read the current frozen parent/exercise eligibility and pin the exact versions. Immutable caller/key/edition/mode fields cannot be rewritten by submit, mark or worker routines. A bounded retry after serialization or unique conflict restarts the whole transaction and checks current capability and committed replay.

Public response reads retain §5.3's repeatable-read or single statement isolation and never hold write ordering locks. Publication and fresh start share stable locks so a new key observes eligible current data or is denied, while a public read begun before withdrawal may finish its coherent old snapshot.

### 6.1 Capability and error precedence

Apply the first failing check in this order. Boundary errors return no resource details: routed media/byte limits (415 UNSUPPORTED_MEDIA or 413 BODY_TOO_LARGE); AUTH validity for private routes (401 AUTH_REQUIRED); scoped CSRF for all unsafe routes (403 CSRF_INVALID); route-level capability (403 FORBIDDEN); bounded syntax/identifier/body validation (400 INVALID_REQUEST); owner/author/resource scope and version membership (404 RESOURCE_NOT_FOUND), followed by shape validation requiring the pinned question type (400 INVALID_REQUEST); route-specific admission/production readiness (429 ADMISSION_LIMIT or 503 SERVICE_UNAVAILABLE, applied before account lookup for public register/resend); post-lock state/deadline (409 ATTEMPT_CLOSED or 409 RESULT_PENDING); If-Match missing 428 PRECONDITION_REQUIRED, malformed 400 INVALID_PRECONDITION, stale 412 REVISION_MISMATCH; then commit or retryable 503 on transient contention. A hidden object always gives the same 404 regardless of state or precondition. Use generic 401 LOGIN_FAILED for invalid credentials. Well-formed but expired, superseded, wrong or consumed verification token gives one generic 400 INVALID_VERIFICATION. Successful verification returns 204 with no authenticated cookie. Register/resend always apply §2.3's uniform outcome independently of account state. GET feedback without authorized reveal is concealed 404; owned result/review before grade is 409 RESULT_PENDING. Start replay conflict is 409 IDEMPOTENCY_CONFLICT.

Private profile and logout require ACTIVE AUTH; no LEARNER role needed. Every attempt route, including history, result, review and feedback, requires ACTIVE verified LEARNER. Scoped author role uses author DTO only, never grants attempt-owner projections. Progress/vocabulary require the same verified learner plus ownership. Loss of learner capability denies any attempt access even if historical ownership exists. Ordinary withdrawal preserves eligible owner history only; it does not preserve lost role entitlement. Anonymous and pending have only public read and PREAUTH identity routes. Unsupported restricted grants default-deny. AUTH/PREAUTH scope selection follows §3.4 before CSRF and never promotes anonymous context. Logout sends no auth cookie clear.

## 7. Question contracts and grading

### 7.1 Typed shapes

| Type | Learner answer object | Protected marking object |
| --- | --- | --- |
| MULTIPLE_CHOICE_SINGLE | {selectedOptionId: UUID} | {correctOptionId: UUID}, membership FK |
| TRUE_FALSE_NOT_GIVEN | {value: TRUE, FALSE or NOT_GIVEN} | {value: same enum} |
| YES_NO_NOT_GIVEN | {value: YES, NO or NOT_GIVEN} | {value: same enum} |

| SENTENCE_COMPLETION | {text: string}, one blank per item | Same protected shape as SHORT_ANSWER |

Every public/learner question shape has id, type, position, prompt and instructions. Include ordered options {id,key,content} only for MCQ and public maxWords for text types. Attempt questions also have points, outside the sample projection. An exercise version requires at least one group and each group at least one valid question. MCQ requires at least two ordered choices, and the other types have no option rows. Null answer uses the outer answer field only. Reject malformed and extra fields, unknown options and wrong enums. Proposed text cap is 2,000 Unicode scalar values. Require positive maxWords and consistent instructions; validate nonempty, unique normalized variants under the same cap and word limit at publish.

### 7.2 Determinism and history

Normalize text using NFC, trim and collapse Unicode White_Space to ASCII space, and use the pinned case-fold operation in §7.4 for case-insensitive comparisons. Preserve punctuation, accents and digits. Count space-delimited tokens containing a Unicode letter or number. Null/normalized empty is UNANSWERED. Valid text above the word limit is INCORRECT. An exact normalized match within limits, exact enum match or correct member option earns full fixed-precision points. INCORRECT and UNANSWERED earn zero. Aggregate one outcome per item, an exact fixed-precision sum and max, and separate correct/incorrect/unanswered counts summing to the question count. No inferred IELTS band.

The frozen exercise version is the sole grader revision reference; retain each revision and its fixture corpus. Persist original item outcomes and result totals. Resolve keys/explanations using the immutable version during authorized review. Changes require a new version and do not rewrite historical outcomes.

### 7.3 Enforceable workload limits

Proposed ceilings, pending TECH-09 performance validation: 20 groups, 100 total questions, 6 choices per MCQ, 12 variants per text item, 2,000 Unicode scalars and 8 KiB UTF-8 per answer or variant, 100 total points, and 512 KiB UTF-8 for the complete canonical versioned grading graph (including text, explanations and feedback inputs). Positive fixed-precision points apply. Cap incoming assessment authoring bodies before parsing at 768 KiB, answer/mark request bodies at 16 KiB, and start at 4 KiB. Bound nesting to the explicit shapes. Count/size checks cover complete drafts on edits and again atomically at publication. Grade at most 100 items and at most 1,200 variant comparisons. Pre-normalize accepted variants at freeze under the pinned revision; never call external services in a grading transaction. Reject over-limit bodies without mutation, and reject invalid graphs without pointer changes.

### 7.4 Canonical input and grader revision

Proposed grader revision GR-1 pins Unicode 15.1.0 data and full default non-Turkic Unicode case folding (not runtime locale lowercasing). Apply to text fields only. Strict UTF-8 transport, no malformed sequences, lone surrogate or U+0000 in decoded text. Pre-parse limits count delivered, decompressed bytes, with bounded decoding or rejected compression. For answer and authored variant fields, enforce ≤2,000 Unicode scalar values and ≤8,192 UTF-8 bytes on both decoded input and normalized output. Limits are conjunctive; an 8,193-byte field may already exceed the scalar limit. Do not truncate.

Normalize in order: NFC → map Unicode 15.1 White_Space runs to one ASCII space and trim → full default case fold if configured → NFC. Preserve accents and punctuation. Count ASCII-space-delimited fields with at least one Unicode 15.1 letter or number. Keep text's exact decoded scalar sequence as persisted answer for nonblank values, and separately store/compute its normalized grading value. Normalize-empty text maps to persisted null before state comparison, same as explicit clear. It never sets a score lock. For nonblank inputs, state equality uses exact original scalar sequence (and exact UUID/enum for other types), independent of grading equality. A stale revision always returns 412 even for equal state. Preserve first authored variant for display; freeze its original text and normalized lookup plus order. Validate every variant has nonzero token count, respects word limit and is unique after normalization.

Budget the graph as UTF-8 bytes of RFC 8785 canonical JSON of an explicitly ordered projection consisting of frozen group/question IDs, display text, version instructions, option/marking/variant entries, normalized variants, answer limits, explanations, evidence excerpts and grader revision. Include excerpt input bytes even when held as references. Encode points as fixed two-decimal strings and require stable list positions. The content publish routine receives structured content and computes or validates the same canonical projection from its complete graph, not a client-supplied byte count. All grade/feedback read inputs must be part of this budget. Keep grading independent of live passage rendering, vocabulary and network calls.

| Literal fixture | Expected state, lock and grade |
| --- | --- |
| null and text containing only tab + NBSP | Persist null, no newly triggered feedback/lock, UNANSWERED |
| café and cafe followed by combining acute | Distinct raw nonblank state, same NFC grade key, both match authored café |
| Straße and STRASSE, case-insensitive policy | Same key strasse; both match within word limit |
| Turkish capital dotted İ with default fold | Normalizes to i plus combining dot; does not match plain i |
| text a tab two spaces b | Grading key a b and two words; raw nonblank value retained |
| a lone JSON surrogate escape or U+0000 | 400 with no state mutation |
| 2,000 four-byte Unicode scalar values in a decoded valid field | 8,000 input bytes, size-valid if normalized also fits; 2,001 scalars rejected |
| 8,193 decoded bytes, or case folding causing one more scalar than allowed | 400; no save/lock, and same rule rejects authored variants |
| Variant “alpha-beta” and answer “alpha beta” | Word counts one versus two; normalized comparison does not equate them |

## 9. Attempts, commands and reveal

### 9.1 Start and finalization

POST /attempts takes {exerciseId,mode}, CSRF and a required opaque Idempotency-Key (16–128 URL-safe ASCII characters). It requires ACTIVE verified learner and derives the canonical pair from immutable attempt mode and the edition's stable exercise ID. Same learner/key/pair replays 200 with original identity even after ordinary withdrawal, without creating an attempt. Different pair yields 409. One created attempt per key via the unique constraint; handle a conflict by checking committed winner after rollback. Return 201 with Location only after commit. Fresh start checks §5.3 and initializes one item per question. New keys on eligible exercises remain independent. Use temporary fair throttles (proposed burst 5 starts and 10 starts/min per account, refill continuously); never impose a lifetime quota or cap simultaneous historical records. Exam pins a server deadline at start; Learning has no deadline.

All updates and finalization lock the attempt row in §5.3 order. For saves/submit take the database decision time in §9.4 after locking; no save/mark is accepted at or after deadline or in terminal state. Finalization freezes every item, computes deterministic outcomes (§7), persists immutable totals, GRADED, reason and timestamps in one transaction. If manual submit takes the lock before deadline use MANUAL and decision time. At/after deadline use TIME_EXPIRED and deadline as effective submitted time. Duplicate submits return stored identical summary. Rollback leaves all item/result states unchanged. GET never finalizes; overdue recovery is read-only and result/review return RESULT_PENDING for authorized owners until finalization. Refresh and reconnect do not extend time.

Expiry scheduling, admission, transaction and retry budgets are defined in §9.5.

### 9.2 Disjoint editing commands

Both commands require owner, ACTIVE verified LEARNER, matching question in pinned edition, CSRF and a shared item If-Match. Apply §6.1 for envelope/ownership gates. Validate the typed pinned question payload after membership, then lock and check state/deadline before evaluating revision. Missing precondition returns 428, stale returns 412 regardless of matching payload. Equality at the current revision is a state no-op, not a retrievable command replay; no timestamp/revision change or newly generated feedback. On timeout or 412 reconcile with GET before deliberately resending. Concurrent answer, mark or submit serialize on the attempt. A successful mutation increments the item revision. Terminal or overdue updates are 409.

- PUT /attempts/{id}/answers/{questionId} accepts exactly {answer: typed object or null}. Reject mark fields. It changes answer only. In Learning with pinned AFTER_EACH_ANSWER, the first valid nonblank answer commits a score lock; syntactically valid over-word-limit answers count as incorrect and lock. Once locked, different answer or clear is 409. Blank, unchanged, invalid, stale and rolled-back requests never trigger feedback.
- PUT /attempts/{id}/marks/{questionId} accepts exactly {markedForReview: boolean}. Reject any answer field, including null. This command cannot mutate the score lock or answer and never emits feedback. A mark remains editable during IN_PROGRESS, before deadline, even with a scoring lock.

The winning answer write computes the permitted item projection from the exact committed answer and immutable version, captures it with that revision, and emits it only after successful commit on that request. A subsequent mark or submit cannot alter the locked input. A lost winning response can recover through the feedback GET using the persisted score lock. A failed commit emits nothing.

### 9.5 Bounded admission, scheduler and recovery

Proposed TECH-09 budget, subject to Product Owner acceptance and benchmark. For Exam only, persist deadline_capacity(bucket_start_utc UTC minute PK, reserved_count integer 0–10, updated_at UTC). A fresh Exam start reserves one slot in its target deadline minute under the bucket row lock within the same start transaction. Request replay never reserves again. To select the candidate bucket, precompute from primary clock plus duration, lock bucket, then sample §9.4 time and recompute. If bucket changed, roll back and retry the whole action once with the same key, otherwise apply the reservation. Never lock a second bucket out of order. At capacity use 429 EXAM_CAPACITY with Retry-After to the next candidate minute, revalidated on retry. Keep reserved counts until the deadline minute has passed. Cleanup may remove old buckets only after the deadline minute plus 24 hours, and clock admission must never target a retired minute. This is temporary global time-window admission, with no permanent retake, account attempt-count or history cap. Per-account transient limits still apply.

Run the worker only in the sole serving process; one in-process scheduler with an atomic single-flight guard. No independently scheduled replica or worker lease is assumed. Tick every 30 seconds; skip a tick if a prior cycle remains active. Use an elapsed monotonic 25-second hard cycle deadline. Scan indexed due keys (partial index over next_eligible_at, deadline_at, id for IN_PROGRESS Exam not parked), at most 100 IDs and 20 claims, with up to 5 retry claims and reserved capacity for up to 15 fresh claims when present. Fairly order due rows within each class; scan past contention with immediate skip-locked claim. Persist attempts.next_eligible_at UTC nullable, failure_count nonnegative integer and parked_at UTC nullable. Initialize an Exam with next_eligible_at = deadline_at and Learning with null; both have failure_count = 0 and no parked_at. Retry mutations cannot alter answer or outcome fields. No account lock in system expiry. Each claim/grade commits atomically in a separate transaction. Never block the scheduler in a batch transaction. Use proposed 100 ms lock wait / 750 ms SQL statement / 1 s whole worker claim deadline, with cancellation and transaction rollback when exceeded. Stop admitting claims with <1 s remaining. Foreground mutations retain bounded 250 ms lock wait / 2 s statement / 5 s whole transaction and a separately reserved execution pool quota so sweep cannot monopolize foreground traffic. Measure overhead separately. If cancellation is uncertain quarantine the connection until verified rollback, keep the worker single-flight, mark readiness degraded, and emit no result until committed.

After grading failure, roll back then best-effort record retry under a new bounded same-attempt transaction if still overdue/ungraded. Delay 1, 2, 4 and 8 minutes at successive failures; after five confirmed failures park for operator investigation. A skipped lock does not count as failure. A lock timeout or crash before retry metadata leaves the attempt eligible at next tick, with the same single-flight/scan bounds. Do not automatically declare a permanent result for parked rows. Authorized submit may still try finalization directly; only an audited operator requeue can unpark after correction without altering answer history. If a healthy attempt is delayed by pool exhaustion or an overdue backlog, return RESULT_PENDING on read and allow authorized submit. Track due count, oldest unparked lag, cycle/budget misses, parked count and capacity rejection, with no sensitive IDs in metrics.

Benchmark proposed accepted load on the selected deployment using 100-item, 512 KiB maximum approved graphs, up to 10 newly due per minute for 30 minutes with aligned boundary bursts and five concurrent foreground submitters. Targets: zero overlapping cycles, all normal cycles ≤25 seconds, p95 finalized lag ≤60 seconds and p99 ≤120 seconds for healthy attempts, zero lost/duplicate results. Catch-up target for 60 healthy due fixtures with no new arrivals ≤5 minutes. Overload test injects 60 due fixtures plus accepted admission traffic and repeated grading failures: overload indicator within 60 seconds, healthy and foreground progress, parked attempts visible, no additional attempt created for a rejected reservation. Measure from pinned deadline to committed grading, report sample sizes and run at least three times. Fail gate and retune capacity, worker or budget if any threshold fails. No M1/M2 dependency on worker tables/runtime.
