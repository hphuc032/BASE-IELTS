## Confirmed design defects

No Critical defect was established in the reviewed documents. The High findings below block sign-off of the current architecture. “Confirmed” means the written contract permits the failure or cannot distinguish the stated cases. It does not imply an implementation is vulnerable.

| ID / Severity | Exact section | Failure scenario and insufficiency | Required correction | Acceptance test |

| V11-H01 · High | v1.1 §§1, 3.1–3.3, 6; TECH-02; SE-01–04 | A Spring Security authentication context remains valid in the backing session after the generation is replaced, or the servlet idle timer advances on excluded traffic and silently diverges. The text does not specify how every protected request is gated or how the backing session lifetime relates to authoritative expiry. | Make the binding the sole authorization gate. Define context persistence, rotation and CSRF reset ordering for JSON login, with generation/account checks before protected handlers, including alternate dispatch or async paths. Document backing-session lifetime so it does not prematurely terminate an otherwise valid auth binding and its touch behavior cannot extend authoritative expiry. Bound pre-auth sessions independently, and define injected failure behavior before/after replacement and context persistence. Do not infer race safety from a concurrent-session setting. | In the version-pinned Spring configuration, force concurrent login and inject context-write/response failure around replacement. Assert at most one authoritative usable context, no usable session on failed activation, exact expiries despite excluded requests, and no protected path authorizes an old cached context. |
| V11-H02 · High | v1.1 §§3.1–3.2, 4; TECH-02/05; SE-03, AD-03 | An operator command commits Admin recovery outside the serving process. Its in-memory mutex is local to that command, so a request authorized before the credential change can still commit afterward. In overlapping deployment or crash takeover, process-local locks also do not fence the old instance. | Choose one durable serialization protocol for identity-sensitive mutations and login rechecks across all actors. For example, use a common database account-row/revision fence for credential changes, operator recovery and protected writes, combined with process-local generation serialization for login/logout. State the global order and checked commit boundary. Fence ingress/process ownership during restart or prohibit overlap with tested stop-before-start. Never use a local lock as the interprocess revocation fence. | Race an independent operator process against a protected transaction and login over separate DB connections. The protected write is ordered before recovery or denied, and rejected state cannot authorize a later request. Kill the app mid-transaction and at deployment handoff. Verify rollback or committed persistence, restart logout and no concurrent serving process. |
| V11-H03 · High | v1.1 §§4, 5.2, 11; TECH-05/12; AD-01–03 | Two operations cannot reliably lock “the governance lock” on a fresh database if the lock is modeled as an absent marker row. Also, a bulk cleanup or credential/verification path could make the last Admin unusable without going through the role API. A two-person proposal gives no enforcement evidence on its own. | Define a stable lock target that exists before bootstrap (precreated singleton or named transaction-scoped lock) and one transaction protocol for all mutations affecting usable Admin status, including cleanup and role/credential/verification changes. Define enforceable distinct approval and operator roles, immutable/auditable success and failure records, credential-delivery policy, and the exact mailbox-attestation rule. Apply scope to later grants and deny undeclared role writers in M1. | Race first bootstrap on empty DB; race all reducing operations including an account cleanup and Admin eligibility change. Assert one initial Admin and at least one usable Admin after ordinary changes. Test recovery with same-person and unprivileged approval, failed recovery rollback, durable audit correlation and old-session rejection. |
| V11-H04 · High | v1.1 §§5.1–5.3, 8, 9.1; DB-01–03 | Updating a draft or publication pointer with independent writes can bypass an application-level “freeze” description. A list reading a pointer and its sample in different snapshots can assemble a mixed edition. Locks are only safe if all mutation paths acquire them in the same order, including read-for-start, withdrawal and parent/child bulk changes. | Define which layer enforces published-row and child immutability, including inserts into a frozen graph, and prohibit generic/direct mutation paths under application privileges. Give a lock acquisition order spanning identity fences and content writes, and use deterministic ordering for multi-parent resources. Run eligibility plus projection on a single consistent read snapshot or statement. State that a read started before withdrawal may return its coherent prior snapshot, and a fresh post-commit read cannot. Define retries for aborted transactions with no externally emitted success. | Reject update, delete and child insertion against a frozen graph via every supported write boundary. Coordinates: hold parent locks during publish/withdraw while starts, draft edits and discovery run. Assert no mixed snapshot, no dangling pointer, no deadlock under supported lock sequences, and correct visibility for post-commit requests. Test failure rollback at each pointer change. |
| V11-H05 · High | v1.1 §§7.1–7.2, 9.1–9.2; TECH-07; RV-01–02 | The complete-state save has only answer and markedForReview. A client sending a changed local draft alongside a mark click is indistinguishable from an answer commit and may lock and reveal. “Mark-only produces no reveal” is an unenforceable intent rule under this DTO. Feedback correctness is also ambiguous under concurrent terminalization unless its projection is bound to the committed answer/version. | Make intent expressible. Use a distinct mark endpoint or discriminated command with mark-only requests unable to carry any answer. Keep shared owner/membership, attempt lock, deadline and revision checks. The only pre-submit reveal comes from a committed first-answer scoring lock in Learning with pinned AFTER_EACH_ANSWER. Compute feedback from that immutable item/version and document failed write or replay behavior. Author and GRADED review projections remain separately gated. | Change a local draft and send mark-only. Expect unchanged stored answer and no reveal. Race first answer against re-answer, mark, submit and another account's read. Inspect all status/DTO shapes, confirming only the winning committed item can yield permitted early feedback. |
| V11-H06 · High | v1.1 §§5.2, 7.1–7.2, 9.1; TECH-09; AT-03, TY-03 | A valid publish can contain arbitrarily many groups, options, accepted variants and aggregate text bytes. Atomic synchronous grading holds an attempt lock while computing and persisting every result. Numeric bounds and per-answer text caps do not bound execution time or expiry queue growth. Unbounded inputs undermine the synchronous protocol and sweep availability. | Add enforceable publish and request bounds for total questions/points, options, variants, bytes and worst-case grading work. Define bounded sweep batches, per-attempt transaction/lock contention behavior and retry/backoff. Document fair temporary request throttles that preserve unlimited retakes. Benchmark accepted limits before M4. | Publish exactly the approved maxima and reject one above each, including aggregate payload limits. Run concurrent submits and overdue sweep on maximum-size fixtures under injected grading failures. Show bounded recovery, no monopolized sweep, one immutable result per attempt and no permanent retake cap. |

Spring requires explicit handling when using custom authentication persistence and concurrency integration. PostgreSQL row locks and transaction deadlocks require consistent lock ordering beyond a local critical section. [Spring Security session management](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html), [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)

## Composite key audit

Each v1.1 §5.1 tuple below has an explicitly declared unique target under the table heading convention. This proves logical eligibility for a PostgreSQL FK, subject to the concrete schema using nonpartial unique targets, matching column types/order, and the stated single-column FKs. It does not prove the existence of migrations. Keep normal nullable matching for the optional child column only, with the required parent independently enforced. [PostgreSQL constraints reference](https://www.postgresql.org/docs/current/ddl-constraints.html)

| Referencing tuple | Referenced unique tuple | Nullability and assessment |
| --- | --- | --- |
| passages(id,current_version_id) | passage_versions(passage_id,id) | Only current_version_id nullable. Same stable parent enforced for a set pointer. |
| exercises(id,current_version_id) | exercise_versions(exercise_id,id) | Only current_version_id nullable. Same exercise enforced for a set pointer. |
| exercise_versions(exercise_id,passage_id) | exercises(id,passage_id) | Required. Confines exercise version to its stable parent. |
| exercise_versions(passage_id,passage_version_id) | passage_versions(passage_id,id) | Required. Confines pinned edition to that passage. |
| questions(exercise_version_id,group_id) | question_groups(exercise_version_id,id) | Required. Constrains exact exercise graph. |
| marking(question_id,correct_option_id) | options(question_id,id) | Option nullable outside MCQ, with independent marking-to-question FK. Enforce type condition separately. |
| evidence(exercise_version_id,question_id) | questions(exercise_version_id,id) | Required. Ties evidence to the question graph. |
| evidence(exercise_version_id,passage_version_id) | exercise_versions(id,passage_version_id) | Required. Enforces exact passage edition pin. |
| evidence(passage_version_id,paragraph_id) | paragraphs(passage_version_id,id) | Required. Rejects a paragraph from another edition. |
| preview_members(exercise_version_id,question_id) | questions(exercise_version_id,id) | Required. Preview PK separately prevents duplicate members. |
| attempt_items(attempt_id,exercise_version_id) | attempts(id,exercise_version_id) | Required. Binds the item to the attempt's immutable edition. |
| attempt_items(exercise_version_id,question_id) | questions(exercise_version_id,id) | Required. Prevents version-crossing question reference. |
| reading_activity(passage_id,passage_version_id) | passage_versions(passage_id,id) | Required. Confines progress to exact version and parent. |
| reading_activity(passage_version_id,last_paragraph_id) | paragraphs(passage_version_id,id) | Optional bookmark only. Prior tuple still enforces version. |
| vocabulary_sources(passage_version_id,paragraph_id) | paragraphs(passage_version_id,id) | Optional paragraph only. Independent version FK is necessary when paragraph is null. See V11-M03. |
| vocabulary_sources(user_id,vocabulary_id) | user_vocabulary(user_id,id) | Required. Enforces source/vocabulary owner agreement, with authorization checked independently. |

A current pointer's FK proves membership, while published state and full graph immutability depend on the transaction/write-boundary controls in V11-H04. Neither the membership constraints nor the locking policy alone prove an authorization decision.
