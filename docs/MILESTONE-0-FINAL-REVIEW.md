## Ranked findings and required corrections

Severity reflects impact if the draft is implemented as written. The corrections below are reviewer proposals until accepted.

### Critical

**C01 · Verification can activate a password chosen before mailbox ownership was proven (§§2.1, 4.1, 7.2).** Registration accepts a password and public verification activates the pending account. The contract does not bind activation to the person who set the password. A recipient following the verification email could activate an account with credentials set by somebody else.

**Required correction.** Adopt an explicit credential-binding flow. Recommended design: collect the usable password during the mailbox-token confirmation flow and atomically set its hash, verify the email and activate the account. Remove password from initial registration and permit a null hash only for the applicable pending state. The verification GET displays confirmation only. The POST consumes the token and sets the password with CSRF protection. Verification creates no authenticated session. Pending duplicate registrations and resends never mutate credentials or profile fields. Add a test that the initial requester cannot authenticate after the mailbox owner finishes activation.

### High

**H01 · Session replacement and expiry lack enforceable atomic semantics (§§2.1, 4.1, 7.2, 9, 11).** The one-session invariant needs a storage choice and a request-time source of truth. An expiry timestamp or session-library setting alone leaves the login/revocation ordering and stale logout behavior unspecified.

**Required correction.** Approve one store and deployment boundary before M1 authorization. In one process, a per-account critical section and authoritative in-memory binding are acceptable if restart invalidates all sessions. For shared deployment, serialize a single account-to-session binding in the shared store. Bind an opaque reference or digest, generation, authenticated_at, last qualifying activity and absolute expiry. Atomically replace the binding and recheck account status and credential/role version before committing login. Activate the fresh ID and send its cookie only after the authoritative change succeeds. Each authenticated request validates the current binding and rejects at or after either expiry boundary. Touch qualifying application requests monotonically without extending absolute expiry. Exclude static/health, public reads and token bootstrap; decide background polling explicitly. Logout and cleanup compare the specific binding before revoking so an old request cannot remove a newer login. Committing sensitive writes after authorization needs a defined revocation fence or serialized policy for in-flight requests. Resolve rotation versus revocation: privilege changes revoke the session and require fresh authentication. Test concurrent logins, old-cookie replay, concurrent touch/revoke, stale logout, both exact timeout boundaries, restart behavior and login racing disablement. [Spring Security session management](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)

**H02 · Verification token lifecycle and M1 email delivery are incomplete (§§0, 2.1, 4.1, 7.2, 9, 11, 13, 15).** The schema tracks use while resend invalidation is prose only. The verification DTO omits CSRF although §9 covers all browser writes. Scope alternates between deferring all email, M1 verification, and requiring production provider selection at exit.

**Required correction.** Bind tokens to a pending user and canonical address or address revision. Store only a unique digest of a cryptographically random token, timestamps, and explicit invalidation or a generation marker. Serialize issuance, resend, consume and account transition on one user lock. Allow at most one live issuance, supersede old tokens on resend, reject expired/used/superseded tokens, and invalidate outstanding tokens on successful activation, address change or disablement. Commit account/token changes before sending, and specify delivery failure and limited retry behavior. Use generic registration/resend responses, per-account and per-source throttles, a configured HTTPS origin, and a confirmation page that avoids referrer, cache, logging and analytics exposure of tokens. Require session-backed CSRF for browser verification POST, consistent with §9. Set TTL, throttles and cleanup before implementing the corresponding behavior. Choose provider-backed M1 delivery or approve a development/test-only mail adapter with production registration disabled until configured. Production deployments must never auto-activate users. Test double consume, resend versus consume, disabled accounts, delivery failure, enumeration resistance and verification CSRF. [Spring Security CSRF guidance](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)

**H03 · Bootstrap identity collision, recovery and last-Admin rules are absent (§§2.1, 8, 10, 11, 13, 15).** “Do not overwrite an existing Admin” leaves ordinary-account collisions, simultaneous provisioning and removal of the final usable Admin undefined.

**Required correction.** Provision through an explicit deployment-operator action reading managed deployment configuration. A one-time command may serve as the entry point for that same mechanism. In a serialized transaction, only create a new, dedicated identity and ADMIN membership after checking a durable bootstrap marker and that no initial Admin already exists. An existing email, including a pending learner, fails closed with no elevation and no password overwrite. Replays do nothing after successful provisioning. Audit the operator action and outcome without secrets, and retire the bootstrap input after success. Define an authenticated operator recovery runbook with auditable identity reset or replacement, revocation of old sessions and no restart-triggered rebootstrap. Protect the last usable Admin under a shared lock across demotions, disablement, deletion and grants. Define how separately authorized operator-provisioned Admins satisfy account activation and administrative login. Add race, collision, replay, restart, recovery and last-Admin tests. Resolve before M1 implementation of bootstrap or lifecycle controls.

**H04 · Composite FK targets and publication transaction were lost during consolidation (§§4, 6, 7.3, 7.6).** The diagram shows membership intent, but independent FKs can still allow mismatched pointers, evidence and responses. Publication must be atomic with public eligibility decisions.

**Required correction.** Restore the exact key matrix from the prior design proposal. Add unique (stable_id, version_no) and (stable_id, version_id) for each version family. Current pointers use (stable_id, version_id); the only permitted null in the pointer is version_id. Exercise versions use (exercise_id, passage_id) and (passage_id, passage_version_id). Questions use (exercise_version_id, group_id). Evidence uses (exercise_version_id, question_id), (exercise_version_id, passage_version_id), and (passage_version_id, paragraph_id). Correct option uses (question_id, option_id). Attempt items use (attempt_id, exercise_version_id) and (exercise_version_id, question_id). Progress and optional vocabulary sources use version/paragraph membership. Explicitly list matching unique targets, nullability, parent ordering, version/order uniqueness and restrictive deletion. Use FK-backed references and test invalid cross-version inserts. PostgreSQL requires a suitable unique target for each composite FK. [PostgreSQL constraints reference](https://www.postgresql.org/docs/current/ddl-constraints.html)

Use a single transaction to lock stable passage then exercise, verify draft revision and validate the full graph, freeze all published rows and switch eligible pointers. Only validated published versions may become current. Public discovery and new starts use the same predicate on exercise, parent and pinned passage version, with consistent lock order on writes. Withdraw by removing eligibility without mutating immutable versions. Document existing-attempt behavior and exceptional takedown separately. Retain original grader behavior and store original outcomes. Keep publication artifacts under restrictive deletion while history depends on them.

**H05 · Early feedback can change the meaning of a graded answer (§§0, 2.1, 6, 7.5, 9).** §0 broadly prohibits pre-submit keys; D09 permits item feedback after answer save. Current wording leaves re-answering, feedback readback, and the exact route-level reveal gates undefined.

**Required correction.** State the single D09 exception in §0. For Learning + AFTER_EACH_ANSWER only, propose that the first valid nonblank answer be committed and locked for scoring before emitting feedback for that item. A clear, validation failure, stale write or mark-only update creates no reveal. If feedback is recoverable, expose a distinct owner-only projection gated by the same pinned mode, policy and persisted item lock. The generic save/recovery DTO stays answer-safe. Exam and Learning + AFTER_SUBMISSION reveal only through authorized GRADED review. Role/scope and reveal are independent mandatory predicates; cross-learner access defaults to deny until defined. Keep author DTOs on separately scoped author routes and all sensitive responses out of caches, SSR payloads and logs. Add negative field and authorization tests for every projection. Keep generic DTO errors free of keys and accepted variants.

**H06 · Public preview policy does not cover stable selection and indirect disclosure (§§2.1, 4.3, 7.3, 9).** The example DTO is answer-free but membership and authoring rules remain underspecified. Per-request rotation could cumulatively reveal more questions than the intended public subset. Public eligibility must also hold on global discovery, slug and related routes.

**Required correction.** Use fixed, explicit versioned sample membership or a deterministic version-scoped count and order. Define integer rounding and cap behavior. Ensure explicit memberships reference questions in the same exercise version. Publish-validate that selectable fields contain no editorial hints, markings or explanations revealing answers. Keep options in authored display order independent of correctness. Use the same allowlist and eligibility predicate across routes, SSR, search, and caching, with withdrawal invalidation or no-store. Test negative cases with draft/withdrawn/restricted parent, mismatched pinned version, non-sample questions, all five type projections and hydrated payloads. Preserve the stated timed-practice boundary: D02 public content and D05 earlier authorized reviews may remain available outside the Exam attempt.

### Medium

**M01 · Attempt retries and grading boundaries need concrete acceptance rules (§§4.4, 6, 7.5).** Persist canonical start identity (exercise ID and mode). An authorized matching replay returns the original attempt across ordinary withdrawal or republishing; a different request is 409. Pin the server clock check after acquiring the common attempt lock. Reject writes at the deadline, including concurrent saves, and finalize all item outcomes and aggregate totals in a single transaction. Propose sweep plus submit-driven finalization, read-only overdue recovery, and a documented pending-result response. Specify replay/no-op semantics for conditional saves, duplicate submit result identity and reason/timestamps. Add tests for save versus submit/expiry, failed grading rollback, repeated submit and history after republishing. Preserve PRD FR-07 navigation, persisted review flags, autosave, refresh/network recovery and manual submit confirmation.

**M02 · Marking and persistence contracts are too abbreviated (§§4–5, 7).** Restore per-type learner and protected DTO tables with exact enum domains, option membership, public word limits and instructions, and versioned normalization fixtures. Define counts for unanswered/incorrect/correct and bounds for points, total score, duration and progress. Add unique role codes, canonical slugs, version numbers and positions. Plan indexes for public publication/topic lookups, FK joins, learner history and optional deadline scans. Avoid duplicating uniqueness-backed indexes. Define the single source for grader policy revision and historical explanation data; any retained duplicate metadata must agree.

**M03 · M1 acceptance and M0 exit gates are out of sync (§§11, 13–15).** Keep identity, authentication, minimal frontend and identity-only migrations. Add resend and confirmation UI/API explicitly if M1 owns verification, or document approved limits for the development/test flow. Separate production deployment requirements from foundation acceptance. Add browser acceptance for cookie attributes and scope, CSRF refresh, production-disabled pre-auth functionality when required configuration is absent, authenticated profile allowlists and frontend auth states. Include negative tests from C01/H01–H03, PostgreSQL concurrency and migration tests, and ownership/role error and audit criteria. Complete or explicitly disposition the toolchain, topology, storage, provider and bootstrap gates before the relevant owner authorization. Replace checked boxes implying closed findings with explicit open status and review references.

**M04 · Current authority and historical documentation conflict (§§0, 10, 14–15 and PRD §§2.3, 6, 18).** Maintain old files as history with an explicit supersession note or a canonical authority index. Identify which PRD requirements still apply, distinguish PRD D-01–D-08 from pack D01–D11, and map old ADR and open-decision IDs. Explicitly supersede earlier JWT options, optional Exam duration/modes, card-only preview and after-submit-only Learning proposals. Update the M1 prompt and links to actual files or rename the canonical documents consistently after approval. Apply precedence to open technical choices without representing them as owner-approved.
