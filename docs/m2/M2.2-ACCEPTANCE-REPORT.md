## Reading domain lifecycle checkpoint

A draft save checks the requested exact edition and expected revision against the loaded state and returns a new revision. The input snapshot stays unchanged on failure. Passage saves preserve retained paragraph IDs, derive positions from array order, and return an explicit update and removal set. A successor starts at revision 1, records the exact frozen base UUID, and receives new edition-owned child IDs. ### Existing V15 persistence contract

V15 at `3a4975e` is the coordinator's committed Passage schema on the catalog branch. This workstream leaves it intact. The guarded repository must use these existing keys and boundaries:

| Operation | Required persistence behavior |
| --- | --- |
| Create Passage and first edition | Insert `content_reading.passages` and its first `content_reading.passage_versions` row together. Set actor from the fenced context. Store version 1 and revision 1 with null lineage and current version. Keep Lesson placement out of the stable identity. |
| Clone Passage | Under the stable Passage lock, load the exact `(passage_id, id)` frozen base and verify no open draft. Use the highest edition number plus one and allocate fresh child IDs. Leave the base rows and current pointer intact. |
| Save Passage draft | Hold the account fence and then the stable Passage lock for the whole transaction. Load the exact edition and ordered paragraphs, check state and revision, and determine the full set of referenced paragraph IDs before deleting any row. Update retained IDs in place, defer `content_reading.passage_paragraph_position_uk` only in the edit transaction for atomic position swaps, and update translations with the graph. CAS on `(passage_id, id, revision)` in state `DRAFT` and append audit in the same transaction. Any failure rolls back the revision, graph and audit together. |
| Read a protected edition | Use the existing F04 staff transaction boundary. Check active capability and exact family membership on the same primary connection. Materialize all authorized fields before releasing the account fence. |

### Exercise storage proposal for coordinator review

The approved ERD requires restrictive composite foreign keys. Bind ExerciseVersion `(exercise_id, passage_id)` to the stable Exercise `(id, passage_id)`, and `(passage_id, passage_version_id)` to V15 `content_reading.passage_versions (passage_id, id)`. For Evidence, bind `(exercise_version_id, question_id)` to the exact question, `(exercise_version_id, passage_version_id)` to the exact ExerciseVersion pin and `(passage_version_id, paragraph_id)` to V15 `content_reading.paragraphs (passage_version_id, id)`. Bind question groups and correct options to the matching version and question respectively. Retain same-root frozen base lineage, one open draft per stable Exercise and the exact mode/duration check on the edition. Frozen versions and descendants require storage guards. Exercise graph writers acquire the stable Passage lock before the stable Exercise lock so that Evidence insertion and paragraph removal serialize. [Approved ERD](M2-ERD.md)
