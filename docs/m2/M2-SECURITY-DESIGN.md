# M2 security design

M2 Design v1.2 · 2026-11-27. Product Owner decisions and release authorization recorded. See the [sign-off package](M2-DESIGN-SIGNOFF.md) and [Decision Register](M2-DECISION-REGISTER.md).

## Authorization matrix

P04 approves the initial policy. Provisioning and runtime paths are design contracts pending separate implementation authorization. Anonymous and PENDING have the same gated public surface. ACTIVE learner has no authoring rights. Identity Admin bootstrap is not a content grant.

| Flow | Anonymous / learner | Admin with CONTENT_EDIT | Admin with CONTENT_PUBLISH | DB principal |
| --- | --- | --- | --- | --- |
| Current public list/detail after M3 gate | Allow only eligible PUBLIC | Same | Same | content_public_reader |
| Staff catalog view/edit | Deny | View and edit through derived catalog capabilities | View only unless independently granted CONTENT_EDIT | content_staff_reader for GET, content_author_writer for edits |
| Passage/Exercise list and detail, exact Passage edition, draft and preview | Deny | CONTENT_VIEW, assigned scope | CONTENT_VIEW, assigned scope | content_staff_reader |
| Publication history and exact operation lookup | Deny | CONTENT_VIEW, root scope and original actor for receipt lookup | CONTENT_VIEW, same root and actor checks | content_staff_reader |
| Create/edit draft | Deny | CONTENT_EDIT, assigned scope | Only if separately given CONTENT_EDIT | content_author_writer |
| Freeze, withdraw, archive | Deny | Deny without CONTENT_PUBLISH | CONTENT_PUBLISH, assigned scope | content_publisher_writer |
| Public marking, older versions, audit | Deny | No through public routes | No through public routes | No public role grant |

Approved P04 limits grants to ACTIVE ADMIN and keeps CONTENT_EDIT and CONTENT_PUBLISH independent. Initial scope is GLOBAL. M1 identity roles have no existing content-scope grant store. CONTENT_VIEW is derived read authority from either active capability. CATALOG_VIEW and CATALOG_EDIT are derived from CONTENT_VIEW and CONTENT_EDIT respectively, with no separate assignable grants. The same Admin can hold both write capabilities. TEACHER and delegated grants stay disabled. Grant changes take the account fence and advance security_revision where authority changes. Content checks capability membership and revision inside its transaction. Actor comes from the trusted AUTH binding. Preserve the [v1.6 allowlist](../MILESTONE-0-FINAL-v1.6.md#541-postgresql-account-fence--m0-adr-16) and apply the approved F04 extension only in M2 implementation.

## Least privilege and threats

- Separate migration owner from writer logins and non-login routine owners. Author calls only typed draft/catalog edits. Publisher calls only publish/withdraw/archive. Staff read policy scopes every object/version tuple. Public SELECT only hardened views/projectors with explicit DTO columns; no direct base table, marking, evidence, explanation or audit access and no role assumption. Review effective grants, PUBLIC defaults, fixed search_path, schema ownership and prepared statements. Use writer-role pool same connection for the account fence and business command.
- Keep all answer-bearing content in separate protected tables. Staff rendering, Next hydration, shared caches, server errors, logs, tracing and search never fall back to a generic graph dump. Public queries, bundles and fixtures contain no secret answer values. Limit question exposure to approved fixed samples. Editorial checks also catch accidental answer hints inside visible text.
- Admit the exact new method/path combinations only. Reuse scoped security context and AUTH CSRF, add new admission limits deliberately, keep fallback deny-all. Unauthenticated unsafe calls never allocate a session. CSRF applies to editor, pointer operations and placement. Retain secure cookies, revision checks and proxy trust.
- Reject unknown body fields including authorId, revision, frozenAt and pointers. Catalog status is accepted only by the explicit status command. Strict projection and scope filters on both listing and nested resource reads deny IDOR. Use bounded JSON and parameterized criteria; allowlisted sorts and immutable ownership. Render content as escaped text; no arbitrary HTML, script URLs or unsafe Markdown rendering.
- Audit all successful status, grant, edit, publish, withdraw and archive decisions using authenticated trusted actor and opaque request references. Publish audit is atomic. Denial telemetry stores safe code only. Counters use fixed labels, not IDs. No write path purges frozen content. Exceptional takedown and retention beyond v1.6 deferred.
- Ingress/projector returns Cache-Control no-store and no shared SSR caching for author/private content. Public uses no-store per baseline. Sample-bearing pages additionally use noindex and sitemap omission after TECH-06. No content uploads in scope. Independent hostile tests are defined in [test plan](M2-TEST-PLAN.md).

## Proposed exact database provisioning boundary

Use dedicated named management login content_grant_operator and non-login content_grant_owner. Only that login receives USAGE on content_grants and EXECUTE on grant_capability(grantee UUID, capability enum) and revoke_capability(grantee UUID, capability enum). No content staff/runtime login receives these grants, no HTTP provisioning route, and no client-provided actor or scope. Map session_user to a pre-provisioned ACTIVE ADMIN grantor using a controlled mapping. Reject unmapped identities and grantor=grantee to prohibit self-escalation. Lock mapped grantor and grantee account rows in UUID order before any grant row. Recheck ACTIVE ADMIN and grantor mapping under lock, write GLOBAL grant/revocation and linked audit, advance grantee security_revision atomically on effective changes, then commit. Repeated no-op changes do not bump revision or duplicate audit. This management transaction has no JVM stripe. After commit stale AUTH cannot authorize a content command; capability reevaluated server-side and inside definer routines. No persistent grant cache. The deployment owner must approve concrete login mapping and access procedures before implementation.

Separate non-login owners with only required column privileges, no PUBLIC EXECUTE and no runtime CREATE. The author login receives exact content_author.edit_draft and typed catalog commands only. The publisher login receives exact content_publisher.publish/withdraw/archive only. Both can invoke the approved actor fence on their transaction connection under v1.6. The staff read login receives only the scoped projectors listed below. The public login gets safe public projections only. The provisioning login cannot author, publish, read marking or impersonate runtime roles.

## Protected staff read boundary

Architecture v1.6 §5.4.1 lists identity_api, content_author_writer, content_publisher_writer and assessment_writer for lockAndCheckActor. F04 approves a narrow M2 implementation extension for the dedicated LOGIN principal `content_staff_reader`: schema `USAGE` on `account_fence_routines` and `EXECUTE` only on `account_fence_routines."lockAndCheckActor"(uuid,bigint)` within that schema, without grant option. Preserve the routine owner and body. For content projections, give that login only the projection schema USAGE and the exact scoped projector EXECUTE allowlist below. Necessary SELECT privileges belong to the corresponding non-login projection owners, scoped to the listed projection and predicate columns. The reader login has no direct table or view access. Deny credentials, lockForLogin, unrelated routines, business INSERT/UPDATE/DELETE, account-table mutation, schema CREATE and PUBLIC EXECUTE. The login cannot assume another role or inherit migration, operator or approver privileges. This is a design requirement for separately authorized implementation. It neither edits v1.6 nor applies a grant.

The application authenticates AUTH and derives actor ID and expected security revision from its trusted binding, then acquires the account row through that routine. An ACTIVE/revision mismatch fails closed. Acquire the shared JVM stripe only after the DB fence and recheck binding generation and expiry. Under the same outer transaction on the same checked-out content_staff_reader connection, check required capability, root/parent/edition scope and execute the scoped projection. Use bounded READ COMMITTED on the primary and a coherent projection statement. Use transaction access mode that permits the locking SELECT (READ WRITE); enforce business read-only behavior by routine privileges, with no DML from GET. Materialize all DTO fields before transaction completion and release of the fence/stripe. No lazy loading, secondary authorization pool, or post-transaction DB access.

If the reader holds the fence first, revocation waits until the DTO is materialized and the read transaction completes. That establishes authorization order; network delivery may lag. If revocation holds it first and commits, the old security revision is denied before projection. Capability grant or revoke continues to take the same account fence, bump revision on effective change and write its own atomic audit. A staff GET writes no publication or governance audit event; safe security telemetry stays outside the content mutation path. Provisioning and withdrawal of DB privileges are controlled and recorded by the migration operator. If this runtime permission is removed, disable the route and drain affected pool connections; a missing grant fails closed. T08/T11 require real PostgreSQL barriers, effective privilege checks and verification that GETs leave business and audit tables unchanged.

## Staff projection allowlist

Map each listed GET family to the scoped routine and named DTO in [Admin endpoints](M2-API-CONTRACT.md#admin-endpoints). The future migration must enumerate each routine signature and the exact columns required for its DTO, joins and authorization predicates. Only the named projection owner gets that column-level SELECT. No schema-wide SELECT, raw graph query or generic table-reader routine.

| GET family | Required scoped projection |
| --- | --- |
| Catalog collection/detail | CatalogAdmin fields, parent membership, pagination and CATALOG_VIEW predicate. |
| Reading/Exercise staff collection | Summary fields, stable root scope, visibility/state and paging predicates. |
| Draft detail and exact Passage edition | PassageAdmin or ExerciseAdmin fields and exact root/edition membership. Private authoring fields are confined to their documented scoped detail. |
| Draft preview | StaffPreview fields and exact draft membership. No marking or private explanations. |
| Publication history | Scoped edition ID, frozen time and current marker. No receipt payload or audit fields. |
| Exact operation receipt lookup | `publication_outcome(root_kind, root_id, operation_id, actor_id, expectedSecurityRevision)` checks current authorization and original actor/root. Read only receipt outcome/result and required predicates. Absent or inaccessible receipts produce the same API 404. No receipt appears on public projections. |
